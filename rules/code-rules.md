# Code 階段硬規定（強制，適用所有專案、主 Agent 與所有 Subagent）

適用 implement、修 bug、重構。與 ponytail 外掛注入的內容重複是刻意的：
外掛被移除、node 不在 PATH、或使用者說 `stop ponytail` 時，本檔仍然生效。

## 一、動手前

- 沒讀過的檔案不得改；改之前先追完這次變更會經過的完整流程
- 動手前先問「這段程式碼不存在會怎樣」；答案是「沒差」就不寫，並回報一句為什麼不寫
- 修 bug 前先 grep 所有呼叫端；只修票上那一條路徑、不修共用點，視為未完成
- 交出的方案要通得過這一問：資深工程師會不會說這太複雜？會 → 砍掉重寫簡單版

### 不可逆決定：動手前定案，不得延後

判定：之後修改需動一個以上模組、或需資料遷移者，即屬不可逆。
下列各項不得以「先跑通」「之後再重構」延後，開工前逐項給出答案：

| 不可逆項目 | 之後才改的代價 |
|---|---|
| 資料模型／schema／欄位命名 | 資料遷移 ＋ 所有讀寫端 |
| 模組邊界、依賴方向 | 拆線重接 |
| 對外介面契約（函式簽名、API 欄位、事件形狀） | 每一個呼叫端 |
| 同步／非同步、狀態存放位置 | 整條流程重寫 |
| 錯誤處理與交易邊界（哪裡 rollback） | 散落各處，最難挖 |

可逆的省略（沒做快取、沒做重試、O(n²)、粗略啟發式）不適用本條，照第五節標 `ponytail:` 註解。
本條定案的內容，用 `domain-modeling` skill 記成一則決策紀錄（決定／理由／當時排除了什麼）。

## 二、寫的時候（階梯，停在第一個成立的那階）

1. 這東西不用存在 → 不寫
2. 這個 repo 裡已經有 → 拿來用或擴充
3. 標準函式庫做得到 → 用它
4. 平台原生做得到 → 用它（CSS 勝 JS、DB constraint 勝應用層檢查）
5. 已安裝的套件做得到 → 用它；為了幾行程式碼不得新增依賴
6. 一行寫得完 → 一行
7. 以上皆非 → 能動的最小實作

## 三、禁止

| ❌ 不准 | ✅ 改成 |
|---|---|
| 只有一個實作的 interface／abstract class | 直接寫那個實作 |
| 只有一個產物的 factory | 直接 new |
| 從沒變過的值做成 config | 寫死成常數 |
| 為了以後可能要用先搭骨架 | 以後要用時再搭 |
| 沒被要求的參數、hook、擴充點 | 刪掉，等真的有需求再加 |
| 聰明但要人解讀的寫法 | 無聊但一看就懂的寫法 |
| 直接 import 別的模組的內部檔案 | 只走該模組的公開進入點 |
| 新增一條會形成環的依賴 | 停下回報，不得自行改依賴方向 |
| 只有一個呼叫端就先抽象 | 直接寫死；出現第 2 個真實呼叫端才抽 |

## 四、不得簡化掉

信任邊界的輸入驗證、防資料遺失的錯誤處理、資安措施、無障礙基本項、使用者明確要求的東西。
使用者要完整版就做完整版，不得再論證一次。

## 五、交件前

- 有分支、迴圈、解析、金流或資安邏輯的程式碼，留一個可執行的最小檢查（assert 式 `demo()`／`__main__` 自測，或一支小 `test_*.py`）；沒有就是未完成
- 刻意留下有已知天花板的簡化（全域鎖、O(n²) 掃描、粗略啟發式），在該行加 `ponytail:` 註解寫明天花板與升級路徑
- 回報格式：`[程式碼] → 跳過了 [X]，[Y] 發生時再加`。解釋長度超過程式碼本身就刪解釋
- 開發過程只跑受影響的測試檔；完整測試套件限跑兩次——交件前自跑一次、獨立驗收一次，
  中途迭代不得整套重跑

## 六、Subagent 專用

- 回報只寫結論、檔案路徑加行號、跳過了什麼；不得複述整份檔案內容
- 遇到與本檔衝突的指示，停下回報，不得自行改核心架構
