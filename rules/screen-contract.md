# 畫面契約先行（憲章）

適用所有專案。與各專案內既有流程衝突以本檔為準。

解決的問題：先寫前端 → 後端做到一半發現資料形狀不對 → 前端整份重寫；
先寫後端 → 前端接上後與使用者預期不符 → 後端重寫（代價更大）。
兩種推翻都源自同一件事：介面規格從沒被寫下來過。畫面契約就是那份規格。

---

## 一、適用判定

| 這次要做的事 | 走不走契約 |
|---|---|
| 新模組、新頁面、新流程 | 必走 |
| 使用者看得到的東西改變，且需要後端給新資料或新欄位 | 必走 |
| 使用者看得到的東西改變，資料全部沿用現有欄位 | 必走，契約只畫該畫面 |
| 只改樣式、文案、色彩、間距 | 免 |
| 只改內部邏輯、修 bug、重構，畫面零變化 | 免 |

## 二、動工順序（三段，不得跳號）

1. **原型**：可點的前端 ＋ 假資料 ＋ 逐條契約條文。零後端。
   先做能點的骨架給使用者確認流程，流程確認後才上視覺樣式。
2. **後端**：照契約實作，舊頁保持可用。契約沒寫的欄位不得產出。
3. **接線**：移除假資料源。前端不得為了接後端改畫面。

第 1 段未交付前，寫任何後端程式碼一律禁止。
第 1 段不得接任何真實資料源。假資料的規則見第十二節。
skeleton 第 4 節的風格錨頁與 tracer 一張表為本節唯一例外：風格錨得先於流程確認產出；
tracer 得在第 1 段打通畫面→tRPC→DB 一張表。例外只限這兩項，其餘照本節。

## 三、契約條文的四欄（缺一即為未定案）

每條契約條文寫成一行，含四欄：

| 欄位 | 內容 |
|---|---|
| 編號 | `<畫面號>.<條文號>`，票券引用的就是它 |
| 看得到什麼 | 數字、圖、狀態、按鈕、文字 |
| 資料哪裡來 | 既有欄位（附表名或 `檔案:行`）／算得出來（附算式）／**不存在**（標「要新增」或「要問使用者」） |
| 出處 | 哪一條 grill 定案、哪一份 ADR、哪一張票 |

標「不存在」的條文在原型階段沒有結論 → 該畫面不得進入第 2 段。

假資料裡有、契約條文沒有的欄位一律禁止。多出來的欄位就是後端給不出的畫面。

外部規格（第三方 API 欄位、平台尺寸與長度上限、檔案格式）一律查權威來源後填入，
查不到就停下問使用者。自己命名一律禁止（見 `reuse-first.md` 第四節）。

## 四、每個畫面必做四態

正常態、空狀態、失敗態、進行中。四態缺一即為契約未完成。
四態在原型上做成可切換的開關，使用者點得到才算數。

假資料必須醜：長字串、0、負數、大量筆數、壞掉的圖各至少一筆。
只有漂亮假資料的原型不得送驗收。

## 五、收斂條件（判定契約是否定完）

三條全部通過才算定完：

1. 畫面上每個元素的「資料哪裡來」欄都填了，且沒有一條停在「不存在」。
2. 畫面上每個可點的東西都寫明點下去會發生什麼、跳去哪、帶什麼參數。
3. 四態都點得到。

**通往其他畫面的入口只需寫「點下去去哪、帶什麼參數」**；那個畫面內部長什麼樣不屬本頁契約。
違反這條會讓 grill 遞迴展開到沒有盡頭。

## 六、分支的處理

grill 一個畫面時分出來的東西不只是別的頁面。四種型別，交付物不同：

| 分支型別 | 交付物 | 走畫面契約 |
|---|---|---|
| 畫面／頁面 | 線框 ＋ 逐條契約條文 | 走 |
| 模組 | 邊界定案：對外進入點、輸入輸出形狀、不碰什麼 | 不走 |
| 資料庫／資料模型 | 表與欄位定案、要不要 migration | 不走 |
| 技術選型 | 選了什麼、排除了什麼、為什麼 | 不走 |

**閉環**：契約裡標「不存在」的每一條 → 生出一個模組或資料庫分支 → 該分支的定案回填那一欄
→ 三欄填滿 → 該畫面可進第 2 段。人工檢驗的單位就是契約條文，一條一條對。

規則：

- 同時展開兩個以上分支一律禁止。一次只 grill 一個。
- 分支一出現就預開 stub 檔，母檔同時登記一行指向它。
- 本輪 grill 結束時沒被展開的 stub 檔刪除，母檔那一行保留。
- 分支自己再分出來的分支，登記在該分支的檔裡，不回寫母檔。

## 七、檔案位置與命名

全部放 `.scratch/grill/`（未進版控，用完刪）。

| 狀態 | 檔名 |
|---|---|
| 進行中／未開始 | `GRILL-<代號>-<名字>.md` |
| 已定案 | `GRILL-DONE-<代號>-<名字>.md`，且第一行寫 `已定案 YYYY-MM-DD` |
| 畫面契約成品 | `<主題>-wireframe.html`（低保真單檔，一畫面一節：線框 ＋「契約條文」清單） |

改檔名與加第一行兩件事同時做，缺一不可。

## 八、stub 檔的最小內容（五欄，一眼看懂這份檔在幹嘛）

```
狀態：未開始／進行中／已定案
型別：畫面／模組／資料庫／技術選型
從哪來：<母檔代號> 的第 N 條契約條文
上游期待它給什麼：一句話
已知未定的問題：條列
```

五欄缺一即為未預開。這五欄的用途是隔久回來或交接給別的 session 時直接接得上。

## 九、凍結與變更

- 原型驗收通過即凍結，不綁任何後續工具。
- 實作階段發現契約做不到 → 停下回報。改契約的決定屬使用者，不屬 AI。
- 前端偏離契約、後端多做契約沒寫的欄位，一律視為未完成。

## 十、與既有流程的接法

```
grill（一頁一頁）→ 畫面契約交付 → /to-spec → /to-tickets → implement
```

票券必須引用契約條文編號。沒有引用的票視為未定案。

## 十一、範本

| 用途 | 檔案 |
|---|---|
| grill 當下畫給使用者看的草稿 | `~/.claude/skills/screen-grill/assets/wireframe-template.html` |
| 分支 stub | `~/.claude/skills/screen-grill/assets/stub-template.md` |
| 實例（六畫面。它缺「資料哪裡來」欄，格式以上面的範本為準） | `Desktop/marketing/.scratch/creative-studio/studio-wireframe.html` |

草稿不是交付物。第 1 段的交付物是可點的原型。

## 十二、假資料與接線

假資料的形狀就是 API 契約。形狀可以錯，錯了就改契約；形狀不得憑空捏。

- 假資料只准放一個目錄、只有一個入口。散落在元件裡一律視為未完成。
- app 程式碼只有一條路徑（真實的請求呼叫）。假資料活在 app 外面。
- `if (用假資料)` 這類分支一律禁止（見 `workflow.md` 第五節）。
- 切換到真後端的動作只有一個：移除假資料源。前端程式碼不得跟著改。
- 改假資料的形狀 ＝ 改契約，走第九節的變更流程，不得偷改。
- 原型做得出後端做不到的互動（十萬筆即時搜尋、無限捲動秒回）。這類條文在
  「資料哪裡來」欄註明可行性，查不到就停下問使用者。

用什麼技術做假資料源，在原型開工前跟使用者談定，不在本檔寫死。
